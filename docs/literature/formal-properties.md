# Формальные свойства для схем синхронизации CDC: литература и практика коммерческих средств

Обзор составлен 20.11.2026 для проекта Open Formal CDC. Тема: какие свойства создают для каждой схемы синхронизации, при каких допущениях, как коммерческие средства их выбирают, доказывают и классифицируют.

Обзор открытых инструментов уже есть в `docs/background.md` и здесь не повторяется.

Обозначения в документе:
- **[Sn]** – номер источника из таблицы раздела 1;
- **«наше предложение»** – вывод автора обзора, в источниках в таком виде его нет;
- **«не проверено»** – сведения из вторичных источников (пересказ поиска, аннотация).

PDF лежат в `refs/pdf/formal-properties/`. Несколько файлов скачаны в соседние каталоги параллельными обзорами (`refs/pdf/metastability/`), в таблице указан их путь.

## 2. Разбор источников

### S1. Kumar, Khan, Mittra – прагматичная формальная методика CDC (главная статья для сравнения)
**Суть.** Infineon вместе с Cadence. Поток из пяти шагов:
1. структурный анализ;
2. функциональный анализ схем синхронизации;
3. формальная проверка с внедрением метастабильности (MSI);
4. моделирование с MSI на уровне SoC;
5. покрытие пар CDC.

Структурные данные и пары CDC берутся из Jasper CDC App. Из них собственный «CDC code generator» (метамодель, Python, XML) создаёт SVA и модель покрытия.

Классы генератора:
- `ndff_sync_check`;
- `pulse_sync_check`;
- `mux_sync_check`;
- `async_fifo_check`;
- `clock_gate_check`;
- `signal_config_check` – проверяет ограничения, заданные для структурного анализа, например что «статический» сигнал действительно не меняется;
- `coverage`.

Пример для импульсного синхронизатора (Listing 3 статьи):
- допущение на ширину входного импульса: `$rose(pulse_i) |-> ##1 !pulse_i[*2] ##1 pulse_i ##1 !pulse_i ##1 !pulse_i`;
- выходной импульс длится один такт: `pulse_o |=> !pulse_o`;
- импульс передаётся: `pulse_i |-> @(posedge sec_clk) ##[0:3] pulse_o ##1 !pulse_o`.

MSI в Jasper учитывает и нарушение setup, и нарушение hold. Поэтому начинают со «свойств, которые проходят без MSI»: любой отказ после включения MSI означает влияние метастабильности. Модель покрытия для каждой пары охватывает четыре случая: нарушение setup с исходом 0 или 1 и нарушение hold с исходом 0 или 1.

Таблица найденных ошибок (Table I) показательна. Функциональный анализ нашёл:
- сигнал, объявленный статическим, на деле менялся;
- сигнал держался слишком мало, чтобы его захватил приёмник.

Ошибки стенда:
- входной импульс шире одного такта;
- потеря данных из-за неверных частот;
- утверждение не учитывало лишний такт задержки при MSI.

**Что взять:**
- набор классов шаблонов почти совпадает с нашим планом;
- обязательно добавить `signal_config_check`: каждое допущение из YAML (статический сигнал, константа режима) проверять утверждением;
- четыре цели покрытия MSI;
- принцип «сначала доказать без MSI, потом с MSI».

**Ограничения.**
- Кода нет; чисел по доказательствам нет (раздел Results качественный).
- В Listing 3 опечатка (`oulse_o`), а свойство передачи импульса смешивает два такта в одном выражении. В немедленной форме yosys-slang это придётся строить автоматом.

### S2. Kumar, Litterick, Candido – RADAR SoC
**Суть.** В абзаце о CDC сказано:
- Jasper CDC проверяет структурные и функциональные свойства, «автоматически созданные по схемам синхронизации»;
- затем эти же свойства доказываются с MSI;
- пользователь может доказывать с MSI и свои свойства;
- свойства и модель MSI выгружаются в моделирование.

**Что взять.** Подтверждение для замысла этапа 5 плана: функциональные свойства блока доказываются с моделью метастабильности.

**Ограничения.** Подробностей и чисел нет.

### S3. Litterick 2006 – SVA для CDC в моделировании
**Суть.** Четыре шага, общих для любого маршрута:
1. структурный анализ;
2. классификация сигналов CDC;
3. выбор свойств;
4. проверка.

Каталог свойств:
- **статический сигнал:** `!$stable(data) |-> !run`;
- **2FF:**
  - вход стабилен три фронта приёмника, если о тактах ничего не известно;
  - `!$stable(d_in) |=> $stable(d_in)[*2]` (в такте приёмника);
  - `p_no_glitch`: асинхронное событие `@(d_in)`, только для моделирования;
- **рукопожатие:**
  - `req |-> req ##1 !req[*1:$] ##0 ack` (на каждый запрос есть подтверждение);
  - `ack |-> s_transfer.ended` (нет подтверждения без запроса);
  - `req |=> $stable(data)[*1:$] ##0 ack`;
- **импульсный синхронизатор (toggle):**
  - вход шириной в один такт источника;
  - выход шириной в один такт приёмника;
  - каждому входу соответствует выход за `##[1:3]` тактов приёмника;
  - промежуток между входными импульсами проверяется свойством стабильности 2FF на триггере переключения;
- **асинхронный FIFO:**
  - `winc |-> !wfull`, `rinc |-> !rempty`;
  - код Грея указателей в домене источника: `!$stable(p) |-> $onehot(p ^ $past(p))`;
  - целостность и порядок данных через счётчики `wcnt` и `rcnt` и локальную переменную.

Модель «дрожания» (jitter) для 2FF: выход случайно появляется на такт раньше, вовремя или на такт позже. Модель умеет и «съедать» импульсы шириной 1–2 такта.

**Что взять.**
- Почти готовый каталог базовых свойств.
- Важная мысль: свойства лучше вешать на экземпляры ячеек синхронизации (через `bind`), а не на разрозненную логику.
- Модель с ранним и поздним выходом – эталон для MSI.

**Ограничения.**
- Работа нацелена на моделирование. Автор сам пишет, что часть свойств (неограниченные диапазоны, асинхронное событие в `p_no_glitch`) для формальной проверки не годится.
- `p_static` в общем случае формально не проверяется: это требование протокола верхнего уровня.

### S4. Litterick 2016 – от RTL до кремния
**Суть.** Требования к 2FF, проверяемые на RTL:
- нет комбинационной логики на пути CDC;
- нет узких импульсов, которые синхронизатор может не увидеть;
- стабильность больше двух активных фронтов, чтобы не было «фильтрации».

Для параллельного синхронизатора (шина в коде Грея):
- код Грея нужно проверять **в домене источника**;
- в домене приёмника коды могут пропускаться, если источник быстрее. Поэтому проверка Грея и проверка стабильности 2FF на стороне приёмника неуместны.

**Что взять.** Свойство «Грей» ставить на регистр источника, а не на выход синхронизатора. Иначе будут ложные контрпримеры при быстром источнике.

**Ограничения.** Основная часть статьи о физической реализации (подцикловые ограничения, разброс задержек бит шины). Формально на RTL это не проверяется.

### S5. Hari, Badaya – покрытие и метрики CDC (Questa CDC)
**Суть.** Пять фаз:
1. проверка настройки (деревья тактов, «чёрные ящики», триггеры с константой);
2. структурный анализ;
3. проверка протоколов синхронизаторов;
4. реконвергенция (код Грея на сходящихся сигналах);
5. устойчивость к метастабильности.

Для каждой фазы введены метрика покрытия и весовая сумма.

SVA протоколов:
- **2FF:** `!$stable(tx) |=> $stable(tx)[*tx_min_cycles]`, где `tx_min_cycles` вычисляется из отношения периодов;
- **мультиплексор:**
  - сигнал выбора держится не меньше двух тактов приёмника;
  - `$rose(enable) |=> $stable(data)[*1:max] ##0 !enable`;
- **рукопожатие:**
  - `data_stable`;
  - `req_has_ack` (подтверждение в пределах двух тактов);
  - `ack_had_req`;
- **FIFO:**
  - `inc |-> !flag` для записи и для чтения;
  - Грей указателей: `!$stable(d) |-> $onehot(d ^ $past(d))`.

Модели оформлены как отдельные модули с `bind`, содержат покрытие и флаги управления. Модель метастабильности вносит метастабильность в один бит шины на один такт.

**Что взять.**
- Понятие «продвижение» (promotion) свойств на найденные синхронизаторы.
- Отдельные метрики: протоколов (`Pt`, `Pu`), синхронизаторов, проверок.
- Для отчёта утилиты: доля переходов со схемой, доля доказанных свойств, доля свойств с покрытой предпосылкой.

**Ограничения.**
- Направлено на моделирование.
- В тексте SVA опечатки (`posdedge`).
- `req_has_ack` с окном «в пределах двух тактов» для асинхронных тактов неверен без допущения о частотах.

### S6. Kapschitz, Ginosar 2005 – формальная проверка синхронизаторов
**Суть.** Классическая академическая основа.

**1. Модель тактов.**
- Несвязанные такты задаются свободными переменными с условием справедливости: каждый такт тикает бесконечно часто.
- «Рациональные» такты m:n задаются недетерминированным циклическим счётчиком. Между двумя фронтами медленного такта лежит `⌊m/n⌋…⌈m/n⌉` фронтов быстрого.
- Слишком свободная модель тактов даёт ложные контрпримеры.

**2. Свойства управления по STG (графу переходов сигналов).** Для каждого события `E`:
- `AG(S(E) & st(E) -> T(E) before! !S(E))` – разрешённое событие происходит, пока разрешено;
- `AG(rise(c) -> OR S(E))` – событие происходит только в разрешённых состояниях.

Алгоритм вычисляет `S(E)` по графу. Пример ошибки, которую ловит такое правило: загрузка данных `L` одновременно с `R1`. При быстром приёмнике данные будут прочитаны раньше, чем записаны.

**3. Проверка передачи данных без привязки к протоколу.**
- Целостность одного бита: `AG(CLK1 & L & DIN(0)=1 -> next_event(CLK2 & E)(S_BUF(0)=1))`. Одного бита достаточно, остальные биты структурно такие же.
- Нет дублирования: `AG(CLK2 & E -> AX((CLK1 & L) before (CLK2 & E)))`.
- Нет потери: `AG(CLK1 & L -> AX((CLK2 & E) before! (CLK1 & L)))`.

**4. FIFO.**
- Модель триггера `FF_nondet`: если вход меняется в такт захвата, выход недетерминированно старый или новый.
- Свойство «любое записанное слово когда-нибудь читается».
- Порядок проверяется индексом записи и чтения.

**Что взять.**
- Модель тактов m:n для YAML.
- «Нет потери и нет дублирования» как универсальное свойство для любой схемы с enable и рукопожатием: его можно ставить, не распознавая протокол.
- Сокращение шины данных до одного бита: оно снижает размер задачи.
- `FF_nondet` – готовая модель MSI.

**Ограничения.**
- CTL и RuleBase, сильные операторы (`before!`, `AF`) – это живучесть. В SBY их нужно переводить в ограниченную форму (счётчик и граница) или использовать живучесть в abc.
- Генерация по STG требует знать протокол, автоматически этого не сделать.

### S7, S8. Li, Kwok и патент Mentor – CDC «на лету»
**Суть (S8).** Свойства по схемам:
- **Грей:** не больше одного бита за такт передатчика.
- **N-тактная стабильность.** `N = ⌊Prx/Ptx⌋ + 1`. Сигнал N-стабилен, если в любом окне из N тактов он меняется не больше одного раза. Даны две формы:
  - полная, сложность O(N²);
  - упрощённая, сложность O(N): `(S0 ≠ S1) → AND(Si = Si+1)`.
- **Рукопожатие, четыре свойства:**
  - (a) `valid` держится до `ack`;
  - (b) `ack` держится до снятия `valid`;
  - (c) новый `valid` не раньше снятия `ack`;
  - (d) данные стабильны, пока выставлены `valid` и `ack`.
- **FIFO:** указатели в коде Грея, нет записи в полный, нет чтения из пустого.

Свойства делятся на два вида:
- с постоянным окном (Грей) – схема сравнения с регистрами задержки;
- с переменным окном (рукопожатие) – свойство превращается в автомат (NFA, затем DFA) и синтезируется в схему.

«На лету»: переходы ставятся в очередь. Для каждого вырезается окрестность из небольшого числа регистров (в формуле патента: меньше 4, 10, 50, 100) с постепенным расширением. Итог: прошло, не прошло, не обработано. Не прошедшие и не обработанные «продвигаются» в последующий маршрут.

**Что взять.**
- Схему «локальная вырезка с ростом окрестности».
- Три итога и «продвижение» нерешённых.
- Обе формы N-стабильности. O(N) дешевле, полная форма даёт больше контрпримеров.

**Ограничения.** S7 прочитан только по аннотации. Формулы (1) и (2) в тексте Google Patents искажены, восстановлены по описанию.

### S9, S10. Plassan и др. – убедительное доказательство CDC на большом SoC (ABC)
**Суть.** Маршрут коммерческого средства (Synopsys):
- сопоставление со структурной библиотекой шаблонов;
- библиотека формальных свойств для найденного шаблона;
- проверка моделей;
- итог «доказано» или «не решено».

Два основных свойства:
- **Coherency:** `stable(DATA_CDC) or onehot(DATA_CDC xor prev(DATA_CDC)) @(posedge CLK1)`. Им же проверяется сходимость.
- **Stability:** `EN -> stable(DATA_CDC) @(posedge CLK1 || posedge CLK2)`.

Главный практический вывод: **неубедительные итоги вызваны в первую очередь недостающими ограничениями**. Это режимы работы, разрешения тактов (clock gating), протоколы на входах.

Метод UsAAR – CEGAR с участием пользователя:
- абстракция локализацией: точки разреза становятся свободными входами;
- старт с комбинационного входного конуса свойства;
- по абстрактному контрпримеру ищется множество «оправдывающих» точек разреза (тернарное моделирование);
- точки классифицируются: такт, сброс, данные, управление;
- пользователю предлагаются простые однобитные допущения: разрешение такта всегда 1, статический сигнал конфигурации, «стоппер» на ненужных данных;
- непринятые точки уточняются автоматически.

Корректность: абстракция – надаппроксимация, поэтому доказательство остаётся доказательством. Абстрактный контрпример зависит только от сигналов в фокусе, поэтому он настоящий.

Числа:
- FIFO: свойства Грея доказываются меньше чем за 1 с. Стабильность без абстракции – тайм-аут 15 мин; с CEGAR – 4–15 мин; с UsAAR – около 10 с при любой ширине данных, так как данные абстрагируются.
- SoC STMicroelectronics (300 тыс. регистров, 7 млн вентилей, 38 доменов тактов): 78 свойств стабильности и 47 Грея.
  - Без абстракции доказано 40 из 125, увеличение тайм-аута не помогает.
  - Первый проход UsAAR вывел 40 допущений настройки, все приняты.
  - После 22 допущений на протоколы рукопожатия доказаны все 125, быстрее в 20 с лишним раз.
  - Достаточные абстракции не больше 200 регистров, хотя конус свойства до 250 тыс. регистров.
- Движки: открытый ABC, `pdr` и `bmc3` параллельно, тайм-аут 15 мин на свойство.

Гл. 5 диссертации: недостающие допущения добываются из нескольких разных контрпримеров. Новые контрпримеры получаются через блокирующие условия. Затем выделяются общие причины и строятся временные допущения.

Пример с рукопожатием в PSL разделяет утверждения и допущения по направлению сигнала:
1. `assert always (!req && !ack) -> next !ack`;
2. `assume always (req && !ack) -> next req`;
3. `assert always (req && ack) -> next ack`;
4. `assume always ack -> next !req`.

Без допущения 2 утверждение 1 даёт контрпример.

**Что взять.** Это **главный источник для архитектуры исполнения**:
- локализация по конусу, рост фокуса по контрпримеру;
- `stopper` для пути данных;
- список типовых недостающих допущений;
- ABC `pdr` и `bmc3` параллельно, лимит 15 мин;
- автоматическое разделение свойства протокола на assume и assert по направлению портов.

**Ограничения.**
- Свойств всего два вида; рукопожатие и FIFO сводятся к стабильности и Грею.
- Коммерческая часть (распознавание схем) закрыта.

### S11. Kalel 2024 – «универсальный квалификатор»
**Суть.** Свойства в SVA:
- `mfs_stable`: `$changed(D1) |=> $stable(D1)[*nb]`, где `nb = Tclk2/Tclk1 + 1`;
- `dataqualifier_stable`: `ctrl |=> $stable(Q1)`;
- `ctrlqualifier`: квалификатор сам держится nb тактов;
- `Exclusivity`: `$onehot0($past(d) ^ d)`;
- «иголка»: счётчик переключений внутри такта, `toggle_count < 2`. Это только для моделирования.

Главный вклад – **универсальный квалификатор**. Коммерческие средства для сложных протоколов берут в качестве управления первый найденный синхронизатор при обходе назад от приёмника:
- для рукопожатия это `req_sync`;
- для FIFO это синхронизированный указатель записи.

Это неверно:

| Схема | Что сообщает средство | Настоящий квалификатор |
|---|---|---|
| простой квалификатор | `ctrl` | `ctrl` |
| рукопожатие | `req_sync` | `req_sync & !ack` |
| асинхронный FIFO | `wrt_add_sync` | `rd_add & !empty_flag` (по рисунку автора) |

Алгоритм `EXTRACT_QUALIFIER`:
- для пути данных от регистра источника до регистра приёмника квалификатор равен конъюнкции условий «управляющий вход вентиля не равен поглощающему значению»;
- для AND берётся `ctrl`, для OR – `!ctrl`;
- для MUX – `sel` или `!sel` в зависимости от входа.

Свойство `stab_p: @(posedge clk_dest) qual_p |-> $stable(d_in_src)`. Доказано (предложение 3.3.2): если `stab_p` выполнено для всех путей данных к регистру, он не может стать метастабильным.

Опыт на CPU (14 доменов, 5,8 тыс. путей данных) в моделировании, 103 теста:
- квалификаторы коммерческого средства: 1,6 тыс. ложных отказов, все на рукопожатиях и FIFO, падают 89 тестов из 103;
- универсальный квалификатор: ни одного отказа.

«Гибридный маршрут»: 24 утверждения о постоянных сигналах конфигурации падали во всех тестах. Значит, настройка CDC расходилась с режимом функциональных тестов.

**Что взять.**
- Алгоритм `EXTRACT_QUALIFIER` прямо на нетлисте Yosys для класса `qualified` в `локальный структурный анализатор`. Это снимает ложные контрпримеры, похожие на 136 контрпримеров `CDC_p_datapath_meta_safe` у Jasper (S24).
- Проверку допущений конфигурации в моделировании и FPV.

**Ограничения.**
- Проверялось моделированием, не доказательством.
- Сигналы на путях данных – только NOT, AND, OR, MUX.

### S12. Стандарт Accellera CDC/RDC 1.0 (март 2026)
**Суть.** Формат абстрактной модели IP (Tcl `accellera_cdc::…`, IP-XACT) для передачи намерений CDC и RDC. Атрибуты, связанные со свойствами:
- `cdc_control_setup` и `cdc_control_hold` («обязателен, если создаются утверждения»): сколько тактов приёмника данные стабильны **до** разрешения и **после** запрета передачи;
- `hamming1` (Грей): на таких входах «создаётся утверждение на переход с расстоянием Хэмминга 1»;
- `clock_period`: нужен для утверждений «быстрый в медленный»;
- `sampling_edge`: нужен для проверки минимальной ширины импульса на однобитном входе синхронизатора;
- логика `glitch_free_combo` и `combo`;
- `reset_assertion_sequence`;
- для RDC – `rdc_control` с блокирующей полярностью и требованием проверить блокировку формально или моделированием.

Минимальная ширина импульса для N-триггерного синхронизатора:
- консервативно – шире двух тактов приёмника;
- мягче – полтора такта плюс setup и hold;
- в общем виде – стабильность на четырёх фронтах такта приёмника.

Классификация переходов:
- открытый контур: один бит; несколько бит с управлением;
- замкнутый контур: рукопожатие;
- код Грея: открытый и замкнутый контур.

**Что взять.**
- Имена и смысл параметров YAML лучше сразу согласовать со стандартом: `cdc_control_setup/hold`, `hamming1`, `clock_period`, `sampling_edge`.
- Позже – импорт и экспорт абстрактной модели.

**Ограничения.** Стандарт описывает намерения и требования, но не сами формулы свойств.

### S13. Real Intent, FMCAD 2016
**Суть.** Формальные проверки Meridian CDC:
- **Data stability** – безопасность передачи данных;
- **Gray code** – реконвергентные управляющие сигналы FIFO;
- **Glitch analysis** – комбинационная логика не создаёт «иголку», которую можно захватить;
- **Pulse width** – управляющий сигнал держится достаточно долго.

Базовая проверка стабильности: переход на передающем триггере приводит к переходу на принимающем на следующем фронте приёмника, при «неуправляющих» значениях остальных входов. Проверка «иголки»: противоположные переходы на нескольких передающих триггерах дают «иголку» на приёмнике.

Итоги: трасса отказа, «прошло» или «прошло с глубокой границей» (deep-bounded pass). Есть параллельный формальный анализ и допущения SVA/PSL на лету.

**Что взять.**
- Класс итога «доказано до глубины N» как отдельный статус.
- Определение «иголки» через противоположные переходы нескольких источников за один такт.

**Ограничения.** Это слайды, формул нет.

### S14. Патент Cadence US 10 769 008 – анализ распространения метастабильности
**Суть.**
- Узлы внедрения: выходы синхронизаторов и пары CDC без синхронизатора.
- Предусловие `METASTABILITY(s)`.
- Свойства `p(i→j)`: «существует функциональный путь от `i` к `j`» при предусловии.
- Рекурсивно по конусу разветвления: если путь есть, узел помечается и создаются свойства к его соседям.
- Узлы, до которых дошли эффекты от нескольких источников, – **точки сходимости метастабильности**.
- Итог – граф: безопасные зоны, затронутые узлы, точки сходимости.

**Что взять.**
- Функциональная (а не структурная) проверка сходимости. Это способ отсечь часть из 233 структурных `convergence_check` Jasper (S24).
- В SBY это свойства покрытия: `cover(изменение j, вызванное изменением i при прочих равных)`, или сравнение двух копий схемы.

**Ограничения.** Формального определения модели метастабильности в доступном тексте нет. Чисел нет.

### S15. Kwok, Viswanathan, Yeung – проверка сбросов
**Суть.**

- Типовые ошибки:
  - нет синхронизатора;
  - логика перед синхронизатором;
  - синхронизатор в одном домене, а потребители в другом;

### S16. Talupuru, Athi – «иголки» на путях CDC
**Суть.** Свойство стабильности ставится на **запускающие триггеры**: `!sync_strobe |=> (T == $past(T))`. Утверждение на выходе комбинационной логики даёт ложное доказательство: RTL без задержек «иголку» не видит.

**Что взять.** Проверку «иголки» формулировать через входы конуса (переходы источников), а не через выход логики.

**Ограничения.** Такты в работе связаны (3:2), для асинхронного случая – только сама идея.

### S17, S18. ZipCPU – асинхронные схемы в SymbiYosys
**Суть.**

Модель тактов:
- `(* anyconst *)` шаг для каждого такта;
- счётчик по `$global_clock`;
- такт – старший бит счётчика;
- шаг больше 0;
- `multiclock on`.

Переключатель тактов:
- выход не меняется без перехода выбранного входа: `!$rose(o_clk)`, если ни один вход не вырос;
- `!(a_sel && b_sel)`;
- `a_sel` меняется только на фронте своего такта;
- первая попытка дала контрпример: `i_sel` переключался туда и обратно до окончания переключения. Добавлено допущение стабильности `i_sel` во время переключения.

FIFO Cummings:
- Грей равен `bin ^ (bin >> 1)`;
- полный и пустой эквивалентны истинной заполненности `f_fill = wbin - rbin`;
- синхронизированные копии указателей не выходят за `2^AW`;
- договор на два значения: `anyconst` адрес и два слова, которые должны выйти по порядку;
- вспомогательные утверждения для индукции;
- `$onehot` в открытом Yosys тогда не поддерживался.

**Что взять.** Почти готовые фрагменты для SBY: модель тактов, договор порядка данных FIFO, свойства переключателя тактов.

**Ограничения.** Это блоги. Проверялись отдельные модули, вручную, без генерации.

### 3.0. Общие соглашения
- **Запись.** SVA-подобная, `@(s)` – фронт такта источника, `@(d)` – такта приёмника, `@(g)` – шаг глобального времени SBY (`multiclock on`, `$global_clock`).
- **Перевод в немедленную форму.** yosys-slang не принимает `assert property`, `$past`, `$stable`. Генератор сразу выдаёт немедленные утверждения с регистрами прошлых значений и счётчиками окон (`локальные заметки`). Сильные (`s_eventually`, `before!`) и неограниченные (`[*1:$]`) формы заменяются ограниченными с параметром `max_latency`; при его нарушении итог «нарушена граница».
- **Предпосылки.** Каждое утверждение с импликацией сопровождается `cover` предпосылки. Без него «доказано» может означать недостижимую предпосылку.
- **Где ставить Грей и стабильность.** На регистрах источника, а не на выходах синхронизатора (S4, S16).
- **Счёт в фронтах приёмника** (наше предложение). Пусть `nd_edges` – число фронтов приёмника с момента последнего изменения источника, считается по `@(g)`. Тогда стабильность не требует знать отношение частот. Отношение входит только через допущения о тактах.
- **Модель тактов (YAML)** (S6, S17):
  - по умолчанию такты свободные, но справедливые: шаг `anyconst > 0`;
  - режим `ratio: [min, max]` – границы числа фронтов одного такта между фронтами другого;
  - режим `fixed: m:n`.

### 3.5. Рукопожатие, 4 фазы (req и ack уровнями, данные под req)
Свойства на стороне источника: S_req – в домене источника, A_s – синхронизированный ack.

| Свойство | Формула | Тип для блока-источника | Источник |
|---|---|---|---|
| req держится до ack | `@(s) req && !A_s \|=> req` | assert, если req – выход блока; assume, если вход | S8 (a), S10 (2) |
| ack держится до снятия req | `@(d) ack && R_d \|=> ack` | по направлению | S8 (b), S10 (3) |
| Нет ack без req | `@(d) !R_d && !ack \|=> !ack` | по направлению | S10 (1), S3 `ack_had_req` |
| Новый req только после снятия ack | `@(s) !req && A_s \|=> !req` | по направлению | S8 (c), S10 (4) |
| **Данные стабильны** от req до ack (до снятия ack для 4 фаз) | `@(g) (req \|\| A_s) && $changed(data_src) -> 0`; вариант S3: `@(s) req \|=> $stable(data)[*1:$] ##0 ack` | assert на блоке-источнике | S3, S5, S8 (d), S11 |
| Каждый req получает ack (ограниченно) | `@(s) $rose(req) \|-> ##[1:Lmax] A_s` | assert | S3, S5 |
| Данные дошли (без протокола) | `@(d) capture && data_dst != data_at_req -> 0` (договор на одно значение `anyconst`) | assert | S6 |

**Квалификатор захвата на приёмнике** не `R_d`, а `R_d & !ack` (S11).

**Ложные контрпримеры:**
- входы протокола (программные запросы) свободны – нужны допущения 2 и 4 (S10);
- в S9 потребовалось 22 таких допущения на SoC;
- окно «ack в пределах 2 тактов» (S5) при асинхронных тактах;
- сбросы сторон раздельные. Нужно отдельное RDC-свойство: после сброса одной стороны протокол возвращается в исходное состояние (аналог CASE-8).

### 3.6. Рукопожатие, 2 фазы (переключения req и ack)
Наше предложение, выведено из S6 и S8: прямой формулировки в найденных источниках нет.
- Нет нового запроса до ответа: `@(s) req != A_s |=> $stable(req)`.
- Данные стабильны, пока запрос не подтверждён: `@(g) (req != A_s) && $changed(data_src) -> 0`.
- Приёмник подтверждает ровно один раз: `@(d) $changed(ack) |-> ack == R_d`.
- Отсутствие потерь и дублей – счётчики `n_req` и `n_ack` как в 3.4.

### 3.11. Статические и квазистатические сигналы, режимы
- Условие статичности: `@(clk) $changed(sig) |-> !run` или `!$stable(sig) |-> !static_cond` (S1, S3).
- **Двойное использование** (S1, S11): в доказательствах CDC это assume, в FPV и моделировании блока – assert. Иначе неверное ограничение тихо скрывает ошибку. У S1 это нашло реальную ошибку RTL.

### 3.12. Комбинационная логика перед синхронизатором («иголка»)
Свойство:
- не формулировать на выходе логики (S16);
- RTL без задержек «иголку» не видит;
- формулировать через переходы источников (S13: противоположные переходы нескольких источников).

Наше предложение – **проверка функционального риска (function hazard)** для конуса `y = f(x)` от триггеров одного домена-источника:

```
@(s) a = $past(x); b = x; m = $anyseq & (a ^ b); v = (a & ~m) | (b & m);
     (f(a) == f(b)) -> (f(v) == f(a))
```

Если на пути от старого к новому вектору функция может пройти через другое значение, захват «иголки» возможен. Если `f(a) != f(b)`, приёмник захватит старое или новое значение, это обычная метастабильность.

Частный случай – «не больше одного входа меняется за такт»: `$onehot0(a ^ b)`.

Для CASE-7:
- дерево ИЛИ с нулями: `f` не зависит от постоянных входов, будет «доказано»;
- Конус с 121 битом источников: ожидается контрпример.

Ограничения:
- **логические** риски вентильной реализации при изменении одного входа RTL-проверка не видит. Здесь нужно структурное правило (на пути только буфер, ИЛИ с константами, `glitch_free_combo` по S12) или проверка нетлиста;
- источники из нескольких доменов не делятся на «старое» и «новое» значение одного шага – такой случай сразу помечать «нет схемы».

### 3.13. Функциональная проверка с моделью метастабильности (MSI)
- **Модель:** первый каскад при изменении входа в шаг захвата берёт старое или новое значение по `$anyseq` (`FF_nondet` из S6). Расширение по S3 и S22: выход может появиться на такт раньше («просачивание»).
- **Поток:**
  1. доказать свойства блока без MSI;
  2. затем с MSI;
  3. новый отказ означает чувствительность к метастабильности (S1).
- **Покрытие:** четыре случая на пару – setup с исходом 0 и 1, hold с исходом 0 и 1 (S1). Для модели «старое или новое» это `cover(инъекция && исход == старое)` и `cover(инъекция && исход == новое)` при росте и спаде.
- **Ложные контрпримеры:** утверждения блока с жёсткой задержкой (S1: «утверждение не учитывало лишний такт»). Их нужно ослаблять до окна `##[n:n+1]`.

**Общее у всех:**
1. Свойства выбираются **по распознанной схеме**. Качество распознавания (особенно квалификатора) определяет число ложных отказов (S11).
2. Свойств мало: стабильность при квалификаторе и Грей/одноединичность покрывают большинство случаев (S9). Рукопожатие и FIFO добавляют протокольные свойства.
3. Без допущений о среде большая часть отказов ложная. На референсном блоке у Jasper 136 из 218. В S9 до допущений доказано 40 из 125.
4. Метастабильность моделируется отдельно (MSI) и проверяется на свойствах блока.

## 5. Выводы для архитектуры и плана Open Formal CDC

### 5.1. Модель и вход
1. **Квалификатор вычислять, а не брать из анализатора.** В `model.py` у перехода класса `qualified` хранить путь данных и вычисленное выражение `qual` по `EXTRACT_QUALIFIER` (S11) на нетлисте Yosys. В `локальный структурный анализатор` добавить вывод этого выражения. Это первая мера против ложных контрпримеров, которыми страдает Jasper.
2. **YAML допущений согласовать со стандартом Accellera** (S12): `clock_period`, `ratio`, `cdc_control_setup/hold`, `hamming1`, `sampling_edge`, `static`, `reset_assertion_sequence`. Позже – импорт абстрактных моделей IP.
3. **Каждое допущение имеет двойника-утверждение** (S1 `signal_config_check`, S11): файл `env_checks.sv` для FPV и моделирования блока.

### 5.2. Шаблоны свойств (порядок реализации)
4. **Этап 2 (план):**
   - Грей в домене источника (3.2, 3.8);
   - рукопожатие: стабильность данных и четыре свойства протокола с разделением assume/assert по направлению портов (3.5, S10);
   - **сразу** `cover` предпосылки для каждого свойства.
5. **Этап 4:**
   - стабильность при квалификаторе `stab_p` (3.7);
   - стабильность и ширина импульса в фронтах приёмника (3.1);
   - одноединичность сходимости (3.3);
   - проверка функционального риска для CASE-7 (3.12).
6. **FIFO:** Грей, переполнение и опустошение, флаги относительно `f_fill`, договор на два значения (S18), отсутствие дублей и RDC-сценарий (CASE-8).
7. **Неограниченные свойства** (`[*1:$]`, «каждый req получает ack») выдавать в ограниченной форме с параметром `max_latency`. Отдельно, по желанию, – живучесть в `abc pdr` с условиями справедливости тактов (S6).

### 5.3. Исполнение (SBY)
8. **Модель тактов** – ZipCPU: шаг `anyconst` и счётчик по `$global_clock`, `multiclock on` (S17, S18). Ограничение отношения частот – режимы `free`, `ratio`, `fixed` (S6).
9. **Локализация как в S9:**
   - старт с комбинационного входного конуса свойства;
   - остальное через `setundef -anyseq` (точки разреза);
   - путь данных – «стоппер» или сокращение до одного бита (S6);
   - при контрпримере – найти точки разреза, от которых он зависит. Начать проще всего: пересчитать трассу, зафиксировав каждую точку по очереди (грубое оправдание). Затем добавить в фокус их конус или предложить допущение.
10. **Движки:**
    - `abc pdr` и `abc bmc3` (или `smtbmc`) параллельно;
    - лимит на свойство 15 мин в S9, у Jasper на референсном блоке – 60 с;
    - в портфель добавить rIC3 (быстрый `Hp` у Jasper – тот же класс IC3/PDR).
11. **Классификация итогов** (объединение S8, S13, S24):
    - `proven`;
    - `cex` – подтверждённый на полном конусе;
    - `cex_abstract` – только на абстракции, требует уточнения;
    - `bounded_pass(N)`;
    - `vacuous` – предпосылка недостижима;
    - `undetermined`;
    - `not_processed`;
    - `no_scheme`.

    Для `cex` отдельно помечать **«контрпример среды»**: в трассе участвуют свободные входы, для которых в YAML нет протокола.

### 5.4. Чем Jasper сильнее и как это повторить
| Сильная сторона Jasper | Как повторить открыто |
|---|---|
| Распознаёт схемы и пользовательские синхронизаторы | `локальный структурный анализатор` и универсальный квалификатор (S11); пользовательские ячейки описываются в YAML: имя модуля, порты req, ack, data |
| Свойства условных исключений: структурное нарушение снимается доказательством (`CDC_p_one_hot`) | Статус «снято доказательством» в отчёте для `convergence`, `glitch`, `sync_chain_logic` при доказанном свойстве 3.3 или 3.12 |
| MSI в формальной проверке и экспорт в моделирование | Подмена первых каскадов моделью `FF_nondet` (S6) или моделью с ранним и поздним выходом (S3). Те же модели годятся для Verilator и Icarus |
| Анализ распространения метастабильности, точки сходимости (S14) | Свойства покрытия «изменение в узле j вызвано инъекцией в i» по конусу разветвления, с ростом от синхронизатора |
| Портфель движков, абстракция (`ar_cex`) | abc pdr, bmc3, rIC3, smtbmc параллельно; CEGAR с локализацией (S9) |
| Удобная отладка | VCD и таблица по тактам (`vcdtab.py`); в отчёте – список свободных входов, от которых зависит контрпример |

**Где можно стать лучше Jasper (по данным референсный блок):**
- покрытие предпосылок (у Jasper 0 покрытий);
- явные допущения среды с проверкой;
- статус «контрпример среды» вместо голого `cex`;
- подсказка допущений из контрпримеров по S10 гл. 5: категории «разрешение такта», «статическая конфигурация», «программный сброс», «вход протокола».

### 5.5. Пополнение `examples/` (верная и испорченная схема для каждого шаблона)
- 2FF: медленный приёмник с коротким импульсом – контрпример; с допущением `ratio` – доказано.
- Рукопожатие: данные меняются до ack – контрпример (S6: `L` одновременно с `R1`).
- Импульсный синхронизатор: два импульса подряд – потеря.
- FIFO: двоичные указатели вместо Грея; раздельные сбросы – CASE-8.
- Квалификатор: рукопожатие, где «первый синхронизатор» даёт ложный отказ, а универсальный квалификатор – доказательство (S11).
- Переключатель тактов: без допущения стабильности `i_sel` – контрпример (S17).
- «Иголка»: ИЛИ с нулями – доказано; XOR двух переключающихся бит – контрпример.

## 6. Открытые вопросы
- Точная формула `CDC_p_datapath_meta_safe` и выбор суффиксов `_k` в Jasper публично не описаны. Можно выяснить на маленьком примере в Jasper: свойство видно в GUI. Это только с согласия пользователя.
- S19 (Cummings 2008) и S7 (Li, Kwok 2009) не прочитаны по существу: нет легального PDF. S19 нужен для MCP-формулировки и FIFO глубины 2.
- Свойства 2-фазного рукопожатия (3.6) и проверка функционального риска (3.12) – наши формулировки. Их нужно проверить на примерах в обе стороны до включения в шаблоны.
